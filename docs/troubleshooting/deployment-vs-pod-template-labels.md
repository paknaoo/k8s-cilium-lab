# Deployment Labels, Pod Templates and Cilium Identities

This document records a label-related policy issue observed during the Phase 8 advanced Cilium policy implementation.

The issue affected policies that selected endpoints by pod labels.

---

## Symptom

A Cilium policy used labels that appeared to be present on a Kubernetes Deployment, but traffic was still denied.

Hubble showed `DROPPED` flows even though the expected allow policy had been applied and reported as valid.

---

## Initial Label Change

A label was added using a command operating on the Deployment resource:

```bash
kubectl label deployment <deployment-name> <label-key>=<label-value>
```

This changed:

```text
metadata.labels
```

on the Deployment object.

It did not change:

```text
spec.template.metadata.labels
```

As a result, the existing and newly managed pods did not necessarily receive the label required by the Cilium policy selector.

---

## Why This Matters

A Deployment is a Kubernetes controller object.

Cilium enforces policy against pod endpoints, not against the Deployment controller itself.

The relevant labels must therefore exist on the pods.

For a Deployment-managed workload, pod labels originate from:

```yaml
spec:
  template:
    metadata:
      labels:
```

A label present only under the Deployment’s top-level:

```yaml
metadata:
  labels:
```

does not become part of the pod identity.

---

## Verification

Deployment metadata and pod-template labels can be compared with:

```bash
kubectl -n <namespace> get deployment <name> \
  -o custom-columns='NAME:.metadata.name,DEPLOYMENT_LABELS:.metadata.labels,POD_TEMPLATE_LABELS:.spec.template.metadata.labels'
```

Actual pod labels can be checked with:

```bash
kubectl -n <namespace> get pods --show-labels
```

Cilium endpoint identities can be checked with:

```bash
kubectl get ciliumendpoints -A -o wide
```

These checks distinguish:

* labels attached to the Deployment;
* labels defined in the pod template;
* labels present on running pods;
* Cilium identities assigned to those pods.

---

## Resolution

The required labels were added to:

```text
spec.template.metadata.labels
```

Updating the pod template changed the Deployment template and triggered a rollout.

Kubernetes created replacement pods containing the corrected labels.

Cilium then assigned endpoint identities based on the new pod label sets.

The policy selectors matched the replacement endpoints and the expected traffic was allowed.

---

## Hubble History

Hubble continued to contain older `DENIED` entries after the configuration had been corrected.

Those flows originated from previous pods created before the required labels were added to the pod template.

The old pods and replacement pods had different endpoint identities.

Historical Hubble events must therefore be interpreted using:

* the event timestamp;
* source and destination pod names;
* pod lifecycle;
* endpoint identity;
* the labels present when the event occurred.

An older denied flow does not prove that the corrected policy is still failing.

Fresh traffic must be generated after the rollout and compared with current pod identities.

---

## Diagnostic Procedure

When a label-based Cilium policy does not match as expected:

1. Confirm that the policy reports `VALID=True`.
2. Inspect the policy endpoint selector.
3. Inspect the Deployment’s top-level labels.
4. Inspect `spec.template.metadata.labels`.
5. Inspect the labels on the current pods.
6. Inspect current Cilium endpoints and identities.
7. Confirm that the Deployment rollout completed.
8. Generate fresh test traffic.
9. Observe the new traffic in Hubble.
10. Separate current flows from events generated by older pods.

---

## Example Checks

Check a Deployment template:

```bash
kubectl -n ccnp-team-a get deployment backend \
  -o yaml
```

Check the protected backend pods:

```bash
kubectl -n ccnp-team-a get pods \
  -l security-tier=protected \
  --show-labels
```

Check the auditor client:

```bash
kubectl -n ccnp-ops get pods \
  -l access=auditor \
  --show-labels
```

Check current Cilium endpoints:

```bash
kubectl get ciliumendpoints -A -o wide |
  grep -E 'ccnp-team-a|ccnp-team-b|ccnp-ops'
```

Generate fresh traffic, then inspect Hubble:

```bash
hubble observe --last 100 -o compact
```

---

## Lesson

Labels used by Cilium must be present on the actual pod endpoints.

For Deployment-managed pods, policy-relevant labels belong in:

```text
spec.template.metadata.labels
```

Changing only the Deployment’s top-level metadata does not update the pod identities used for policy enforcement.
